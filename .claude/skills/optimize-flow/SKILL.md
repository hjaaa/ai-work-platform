## User Input

```text
$ARGUMENTS
```

## 设计理念

> "AI 的错误不是你的损失，而是你最宝贵的知识原料。"
> 每次沉淀都让下一次需求开发更快、更准。

本 skill 是知识沉淀的**唯一入口**，是复利引擎的写入端。
`/req-dev` 是读取端——它从 experience/ 加载经验；本 skill 向 experience/ 写入经验。

## 两种使用方式

### 方式 1：直接描述经验（快速模式）

用户直接告诉 AI 要记录什么：

```
/optimize-flow Apollo 的 When-Then 格式必须用 && 连接条件，AI 总是用逗号
/optimize-flow 商品发放时钱包类型要区分现金钱包和积分钱包，不能混用
/optimize-flow 雅典娜创建商品后必须等 3 秒再查询状态，否则会查到旧数据
```

→ 直接跳到 Step 3（结构化写入）。

### 方式 2：从需求中提取（引导模式）

用户没有具体描述，或在需求完成后触发：

```
/optimize-flow
/optimize-flow 沉淀一下刚才的经验
```

→ 从 Step 1 开始引导。

## 执行步骤

### Step 1: 收集经验素材（引导模式）

按优先级从以下来源收集：

**来源 A：notes.md**
- 找到最近活跃的 `requirements/{id}/notes.md`
- 提取所有条目，特别是标记为"是否需要沉淀到 experience/：是"的

**来源 B：当前对话**
- 回顾本次对话中用户纠正过 AI 的地方
- 回顾遇到的意外问题和解决方案

**来源 C：主动提问**
如果以上都没有素材，问用户（最多 3 个问题）：

```
1. 这次开发中 AI 犯过什么反复出现的错误？
2. 有什么技术约束是事先不知道、靠排查才发现的？
3. 下次做同类需求，最应该提前知道什么？

（回答任意一个即可，输入 "skip" 跳过）
```

### Step 2: 确认沉淀内容

展示收集到的素材摘要：

```
## 待沉淀的经验：

1. [经验摘要 1]
2. [经验摘要 2]

确认沉淀？（输入 "ok" / 修改编号 / "skip" 跳过）
```

如果用户要修改，允许调整后再继续。

### Step 3: 确定场景和文件类型

对每条经验：

1. **识别场景名**：从内容提取核心场景关键词
   - 业务场景：商品发放、支付对接、活动配置...
   - 技术场景：Apollo配置、Redis缓存、MQ消息...
   - 通用场景：数据库操作、接口对接、部署发布...

2. **确定文件类型**：

| 经验类型 | 写入文件 | 判断标准 |
|----------|----------|----------|
| 具体的错误案例 | `common-errors.md` | "AI 做 X 时犯了 Y 错误" |
| 字段格式/配置要求 | `field-specs.md` | "某字段必须是 XX 格式" |
| 操作前检查清单 | `self-check.md` | "做 X 之前要先检查 Y" |
| 走不通的路 | `dead-ends.md` | "尝试 X 方案失败，因为 Y" |

3. **检查目录**：`context/experience/{场景名}/`
   - 不存在 → 创建
   - 已存在 → 追加到对应文件末尾

### Step 4: 结构化写入

**common-errors.md 格式**：

```markdown
## [YYYY-MM-DD] [简述]

- **现象**：[AI 做了什么 / 出了什么问题]
- **原因**：[缺少什么信息导致的]
- **正确做法**：[具体的、可执行的修正]
- **适用场景**：[什么时候需要注意]
```

**field-specs.md 格式**：

```markdown
## [字段/配置名]

- **格式要求**：[具体格式]
- **常见错误**：[AI 容易犯的错]
- **正确示例**：[示例值]
```

**self-check.md 格式**：

```markdown
## [场景名] 自检清单

- [ ] [检查项 1]
- [ ] [检查项 2]
- [ ] [检查项 3]
```

**dead-ends.md 格式**：

```markdown
## [YYYY-MM-DD] [简述]

- **尝试了**：[方案描述]
- **结果**：失败 / 部分成功
- **原因**：[为什么走不通]
- **不要再试**：[明确告诫，防止下次重蹈覆辙]
```

**写入规则**：
- 追加到文件末尾，不覆盖已有内容
- 如果文件不存在，创建并写入
- 每条经验控制在 5-10 行以内

### Step 5: 更新经验索引

读取 `context/experience/index.md`：

1. 如果该场景在索引中已有条目：检查关键词是否需要扩展
2. 如果是新场景：添加新行

```markdown
| 关键词1, 关键词2, 关键词3 | experience/{场景名}/{文件名} | {加载时机} | {置信度} | {一句话简述} |
```

**加载时机判断**：
- 业务规则/需求理解 → "需求分析时"
- 技术方案/架构选择 → "方案设计时"
- 编码/配置细节 → "实施前"

**置信度规则**：
- 新沉淀的经验默认为 **低**
- 第二次遇到同样问题并确认有效 → 升为 **中**
- 第三次验证、或涉及资金/安全/数据一致性 → 升为 **高**
- 被证伪的经验 → 降级或删除，不静默保留
- 置信度为"高"的经验，触发升级检查（见 Step 6）
- 被证伪的经验 → 降级或删除，不静默保留

**重要**：如果索引中还有"暂无条目"占位行，写入第一条真实条目时删除它。

### Step 5.5: 置信度升级检查

当更新一条已有经验的置信度时，检查是否触发升级：

**升为"中"时**：无特殊动作，正常更新索引。

**升为"高"时**：判断这条经验是否可以机械化检查：
- **可以**（有明确的 grep 模式或代码模式）→ 提醒用户升级为 lint 规则：
  ```
  📋 这条经验已被验证 3 次以上，建议升级为 lint 规则：
  
  当前经验：[经验摘要]
  建议规则：
    ID: L0XX
    检查模式: [grep 模式]
    修复指令: [具体怎么修]
  
  是否写入 context/rules/lint-rules.md？（yes/no）
  ```
  用户确认后，在 lint-rules.md 的规则表中追加新行，来源标注为 `experience/{场景名}`。
  
- **不可以**（需要语义理解，无法用 grep 检查）→ 建议升级为 `context/team/` 正式规范或 `context/rules/pattern-rules.md` 代码模式。

### Step 6: 输出确认

```
✅ 经验沉淀完成

写入：context/experience/{场景名}/{文件名}
索引：experience/index.md 已更新（置信度：低）
复利预期：下次遇到 [{关键词}] 相关需求时，/req-dev 将自动提醒此经验
```

如果触发了 lint 升级：
```
🔧 Lint 规则已追加

规则 L0XX 已写入 context/rules/lint-rules.md
Stop hook 下次运行时将自动检查此规则
从"经验提醒"升级为"自动拦截"，无需人工记忆
```

## 行为规则

- 用户说 "skip" / "跳过" / "没有" → 立即结束
- 每次沉淀不超过 5 条（多了说明粒度太粗）
- 不修改 `context/team/` 下的文件（需正式变更 constitution）
- 不修改 `context/rules/` 下的文件（除非用户明确要求）
- 写入时追加不覆盖
- 快速模式（方式 1）应在 30 秒内完成，不要过度询问
