# 错误码

> 《Java 开发手册（黄山版）》二、异常日志（一），含项目化裁剪（与原书差异见 git 历史）

**【项目调整】** 本项目不采用原书的五位字符错误码体系（A/B/C + 四位数字编号）及其附表。统一响应封装为 `com.aiwork.common.core.util.R`：`code` 为 int 型，取值见 `CommonConstants`（0 成功、1 失败），出错原因由 `msg` 字段承载；业务异常统一抛出并由全局异常处理器（`GlobalBizExceptionHandler`）转为 `R` 错误响应。禁止在业务代码中自造字符串错误码。原书与该体系强绑定的条目已删除，保留以下通用原则：

1. 【强制】错误码的制定原则：快速溯源、沟通标准化。

    **说明**：错误码想得过于完美和复杂，就像康熙字典的生僻字一样，用词似乎精准，但是字典不容易随身携带且简单易懂。

    **正例**：错误码回答的问题是谁的错？错在哪？

    - 1）错误码必须能够快速知晓错误来源，可快速判断是谁的问题。
    - 2）错误码必须能够进行清晰地比对（代码中容易 equals）。
    - 3）错误码有利于团队快速对错误原因达到一致认知。

2. 【强制】错误码不体现版本号和错误等级信息。

    **说明**：错误码以不断追加的方式进行兼容。错误等级由日志和错误码本身的释义来决定。

3. 【强制】错误码不能直接输出给用户作为提示信息使用。

    **说明**：堆栈（stack_trace）、错误信息（error_message）、错误码（error_code）、提示信息（user_tip）是一个有效关联并互相转义的和谐整体，但是请勿互相越俎代庖。

4. 【推荐】错误码之外的业务信息由 `msg`（错误信息）来承载，而不是让错误码本身涵盖过多具体业务属性。
